# TL002: Potential single-partition write bottleneck

## Detection and evidence

A known Spark DataFrame's `.coalesce(1)` result reaches a recognized terminal
write. Evidence identifies both Spark origin and the single-partition call;
the diagnostic is located at the **write**. Aliases and supported writer options
preserve the evidence. A recognized intervening repartition/shuffle can drop it.

```python
from pyspark.sql import SparkSession

df = SparkSession.builder.getOrCreate().table("events")
export = df.coalesce(1)
export.write.mode("overwrite").parquet("export")  # TL002
```

## Non-triggering example

```python
from pyspark.sql import SparkSession

df = SparkSession.builder.getOrCreate().table("events")
export = df.coalesce(1)  # No write: not a finding by itself.
export.repartition(8).write.parquet("export")
```

Unknown transformations or wrappers can lose evidence and hide a later write.
Partition provenance is not an estimate of data size, write duration, output file
count, or runtime partition behavior under all Spark configurations.

## Review and suppression

**Question:** Is a small single-partition export intentional, or does this
unnecessarily serialize a large write? Preserve required output semantics.

```python
export.write.csv(
    "export"
)  # torchlight: ignore[TL002] -- small single-partition export required
```

Place the reason on the write's first or last line, not the earlier coalesce.

## Version and policy notes

Warning; no autofix. Supported V1 and V2 terminal writes are modeled, but there is
no Spark-version filter. Validate advice against the deployed Spark distribution.
No real-world precision estimate is published yet. [All rules](README.md).
